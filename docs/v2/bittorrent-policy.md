# Серверная политика ограничения BitTorrent

Политика реализует строгий сетевой режим: она не пытается распознать BitTorrent по портам или сигнатурам, а запрещает произвольный исходящий трафик клиентов и разрешает только утверждённые сочетания `протокол + IPv4-подсеть + порт`. Поэтому TCP peer handshake, uTP/DHT по UDP, нестандартные порты и зашифрованный BitTorrent блокируются, если конечная точка не внесена в список разрешений.

Это не абсолютная гарантия распознавания BitTorrent. Разрешённый HTTPS-сервис, который сам предоставляет туннель или произвольный proxy/CONNECT, остаётся возможным обходом. Такие назначения нельзя включать в строгий список без отдельной оценки.

## Безопасное состояние по умолчанию

`VPNCHAIN_BT_POLICY_MODE` по умолчанию равен `disabled`. Репозиторий не включает адреса production, а `policy/allowed-egress.policy` намеренно не содержит активных правил. Поэтому получение или запуск этого кода само по себе не включает фильтрацию.

Режимы:

- `disabled` — удалить только цепочки `VPCBTRU`/`VPCBTAM`, принадлежащие этой политике;
- `audit` — пропустить трафик, но считать пакеты на завершающем правиле без записи адресов или содержимого пакетов в журнал;
- `enforce` — разрешить только утверждённые записи, остальное завершить `DROP`; IPv6 forwarding с клиентского интерфейса также закрывается.

Для strict allowlist допустимы только строки вида:

```text
tcp 192.0.2.10/32 443
udp 192.0.2.53/32 53
```

Адреса примера зарезервированы для документации. В реальном runtime-файле нужны утверждённые назначения. Запрещены доменные имена, `0.0.0.0/0`, протокол `all`, диапазон `any` и пустой список для `enforce`.

## Проверка кандидата без применения

```bash
VPNCHAIN_BT_POLICY_MODE=enforce \
VPNCHAIN_BT_POLICY_ROLE=ru \
VPNCHAIN_BT_ALLOWLIST=/etc/vpnchain/bittorrent-policy/allowed-egress.policy \
/usr/local/sbin/vpnchain-bittorrent-policy check
```

Команда проверяет режим, роль, имя интерфейса и каждую запись списка. Она не меняет firewall. До rollout следует отдельно проверить синтаксис кандидата в одноразовом контейнере или сетевом пространстве имён.

## Apply, read-back и rollback

Ниже приведён runbook, а не инструкция включить production без change gate.

1. Сохранить полный внешний backup firewall и маршрутизации в защищённый каталог узла.
2. Проверить административный доступ из второй независимой сессии.
3. Установить внешний автоматический rollback timer.
4. Установить `VPNCHAIN_BT_POLICY_MODE=audit` или `enforce` только в утверждённом runtime-окружении.
5. Запустить контейнер штатным lifecycle или выполнить внутри него:

```bash
vpnchain-bittorrent-policy apply
vpnchain-bittorrent-policy read-back
```

`apply` создаёт закрытые snapshot-файлы `iptables-save` и `ip6tables-save` в `/run/vpnchain-bittorrent-policy`, проверяет candidate через restore test mode, загружает проектные цепочки и подключает их первой позицией к `FORWARD`. Повторный запуск не дублирует jump. Ошибка active apply устанавливает минимальный принадлежащий проекту `DROP` guard вместо fail-open.

Для немедленного отката текущего apply:

```bash
vpnchain-bittorrent-policy rollback
```

Rollback восстанавливает полные IPv4/IPv6 snapshots, а не удаляет правила по одному. Runtime snapshots могут содержать чувствительную сетевую топологию: их нельзя копировать в Git, Kanban или общие логи.

## Проверки перед разрешением rollout

Обязательны:

- lint/static/unit/integration тесты и проверка секретов;
- изолированный container/network-namespace тест: обычное разрешённое HTTPS/DNS проходит, TCP peer и UDP/DHT к неразрешённым назначениям блокируются, нестандартные порты блокируются;
- повторный apply не создаёт дубликаты;
- полный rollback возвращает baseline;
- IPv6 не даёт обхода;
- restart/reboot восстанавливает политику до открытия клиентского forwarding;
- независимое review точного commit и Sonar Quality Gate.

При любом несовпадении read-back, потере управления, неожиданном direct egress или отказе разрешённого трафика rollout остаётся `NO-GO`, выполняется полный rollback.
