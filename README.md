# AmneziaWG Proxy-Chain — прокси-цепочка 🛡️

Решение на базе протокола **AmneziaWG (WireGuard с защитой от DPI)** для создания устойчивой двухузловой прокси-цепочки.

Проект позволяет развернуть два узла для прозрачного и **селективного** роутинга трафика. Входной узел поддерживает клиентские слоты через переменные окружения `CLIENT_PUB_KEY` … `CLIENT17_PUB_KEY`:
1. **Входной узел (РФ)** — принимает AmneziaWG-подключения от клиентов. Трафик к российским IP-адресам пускается **напрямую** (без потери скорости), весь остальной — через второй туннель.
2. **Выходной узел (Зарубежный)** — принимает туннелированный трафик и выпускает его в глобальную сеть.

## Особенности текущей развёртки

| Параметр | Входной (RU) | Выходной (AM/NL) |
|---|---|---|
| ОС | Debian 11 (Bullseye) | Debian 13 (Trixie) |
| Ядро | `5.10.x-amd64` | `6.12.x-amd64` |
| **Модуль ядра** | ✅ `amneziawg.ko` (PPA) | ✅ `amneziawg.ko` (DKMS) |
| **Режим работы** | **режим ядра** | **режим ядра** |

> **Важно:** Оба сервера работают в **режиме ядра** (через модуль ядра `amneziawg`), а не через реализацию в пользовательском пространстве `amneziawg-go`. Это обеспечивает максимальную производительность и стабильность.

## 📡 Мониторинг и автовосстановление канала

Скрипт `monitor_tunnel.sh` периодически отправляет ICMP-пакеты между узлами и пишет потери/задержки в `/var/log/awg_monitor.log`.

```bash
# Запустить на RU-сервере: мониторинг канала до AM/выходного сервера
./monitor_tunnel.sh <IP_AM_СЕРВЕРА> [INTERFACE]

# Пример для текущей proxy-chain схемы: контролировать awg1 до выходного узла
./monitor_tunnel.sh <IP_AM_СЕРВЕРА> awg1
```

Если потери превышают **20%**, скрипт запускает восстановление с паузами между попытками `0 / 5 / 15` минут, максимум 3 попытки. Восстановление ищет владельца интерфейса:

- если интерфейс управляется внутри контейнера `awg-ru`, выполняется `docker restart -t 20 awg-ru`;
- если конфиг есть на хосте в `/etc/amnezia/amneziawg/<interface>.conf`, выполняется `awg-quick down/up`;
- если владелец не найден, в лог пишется `ERROR` без фиктивного рестарта.

Скрипт не хранит ключи и логирует только события проверки здоровья и восстановления.

## ❓ О совместимости с VLESS

AmneziaWG работает поверх **UDP** и модифицирует заголовки пакетов для обхода DPI. VLESS работает поверх **TCP/WebSocket/gRPC** (Xray-core/Sing-box) — это принципиально разные транспортные уровни, поэтому встроить один в другой технически невозможно.

**Варианты совместного использования:**
1. Поднять Xray-core (VLESS) **параллельно** на том же узле — как резервный транспорт.
2. Завернуть VLESS-трафик **через** существующий AmneziaWG-туннель.

## Состояние менеджера v2

Текущая версия содержит менеджер на SQLite из стандартной библиотеки Python, одноразовую генерацию клиентских конфигов, парсер активности и локальный веб-интерфейс/API. Для новой установки начинайте с [`docs/v2/quick-start.md`](./docs/v2/quick-start.md) и пошагового bootstrap-скрипта:

```bash
# 1. На AM/выходном сервере поднять AM как обычный AWG-сервер
sudo scripts/vpnchain-bootstrap.sh --role am --apply

# 2. На AM/выходном сервере сгенерировать готовый клиентский конфиг / awg1.conf для RU
sudo scripts/vpnchain-bootstrap.sh \
  --role am \
  --generate-ru-uplink \
  --am-endpoint '<AM_HOST>:51821' \
  --output /etc/vpnchain/ru-awg1.conf \
  --apply

# 3. Скопировать /etc/vpnchain/ru-awg1.conf на RU-сервер и запустить RU.
# --server-endpoint сохраняется в env и автоматически попадает в клиентский конфигs.
sudo scripts/vpnchain-bootstrap.sh \
  --role ru \
  --ru-uplink-conf /etc/vpnchain/ru-awg1.conf \
  --server-endpoint '<RU_HOST>:51820' \
  --apply
```

Скрипт проверяет root/Docker/Compose/kernel module, создаёт runtime-каталоги, сохраняет старый env-конфиг в резервную копию перед заменой и печатает следующие шаги для ключей, peer'ов, WebUI и проверки.

## Веб-интерфейс vpnchain-manager v2

Доступен небольшой локальный WebUI/API для администрирования клиентских профилей без новых runtime-зависимостей.

```bash
# Локальный режим: инициализировать/использовать БД менеджера и открыть http://127.0.0.1:8080
python3 -m vpnchain.cli --db ./vpnchain.sqlite webui

# Локальный интерфейс, подключённый к активному v2-серверу по SSH. Браузер всё равно ходит только на localhost.
python3 -m vpnchain.cli webui \
  --remote <ssh-host> \
  --remote-db /var/lib/vpnchain/vpnchain.sqlite \
  --interface awg0 \
  --activity-tool awg \
  --ssh-option "-o BatchMode=yes"
```

Веб-интерфейс умеет:

- показывать список профилей и состояние включён/отключён;
- создавать новый профиль из формы;
- один раз показать/скопировать/скачать сгенерированный клиентский конфиг после создания;
- включать, отключать и удалять профили;
- показывать активность (`latest_handshake`, `rx`, `tx`, `endpoint`), если доступен `wg show <interface> dump` или `awg show <interface> dump`.

В режиме `--remote` WebUI остаётся привязанным к localhost, но операции с профилями выполняются на активном сервере через SSH вызовом `vpnchain --db <remote-db> ...`; активность читается через `wg/awg show <interface> dump` на том же сервере. На удалённом хосте уже должен быть установлен v2 manager CLI, а SSH-пользователь должен иметь права на выбранную БД и activity-команду.

Если live-дамп недоступен или процессу не хватает прав, активность показывается как unknown/offline без падения UI. Тесты используют seams парсера/сервиса и не требуют root или реального SSH-сервера.

### Краткая справка по API

- `GET /api/peers` возвращает публичные строки профилей плюс активность.
- `POST /api/peers` создаёт профиль из полей формы или JSON (`name`, необязательное `address`, `platform`, `client_type`, `export_profile`, `notes`, `server_public_key`, `server_endpoint`) и возвращает одноразовый `client_config`. Если server-поля не переданы, CLI/manager берёт `VPNCHAIN_SERVER_PUBLIC_KEY` и `VPNCHAIN_SERVER_ENDPOINT` из окружения.
- `POST /api/peers/<name>/enable`
- `POST /api/peers/<name>/disable`
- `POST /api/peers/<name>/delete`

### Безопасность

По умолчанию WebUI слушает `127.0.0.1` и не имеет встроенных TLS/CSRF-защит. Считайте его локальным инструмент администрирования. Для доступа из браузера держите привязку к localhost. `--remote` управляет серверным VPN-состоянием через SSH, но не публикует сам WebUI наружу. Если намеренно открываете UI через обратный прокси, добавьте авторизацию, TLS и контроль доступа.

Приватные ключи клиентов появляются только в одноразовом ответе/конфиге при создании. Они не хранятся в SQLite; их нельзя коммитить в git, вставлять в документацию или оставлять в общих логах.
